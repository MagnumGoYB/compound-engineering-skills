# Compound Plan

> 把想法变成蓝图。80% 的思考发生在代码被写出来之前。

## 目标

产出清晰、可执行的实现方案，让 Work 阶段可以零思考执行。

## 流程

### 1. 理解需求

- [ ] 弄清问题的本质（不是用户说要什么，而是用户需要什么）
- [ ] 明确约束条件（时间、技术、资源）
- [ ] 定义成功标准

### 2. 研究代码库

- [ ] 查找同类功能的现有实现
- [ ] 理解现有架构和设计模式
- [ ] 识别可复用的组件和工具

### 3. 查阅文档

- [ ] 框架官方文档的最佳实践
- [ ] API 文档和类型定义
- [ ] 相关的 ADR（架构决策记录）

### 4. 设计方案

- [ ] 列出 2-3 个可行方案
- [ ] 分析各方案的优劣
- [ ] 选择推荐方案并说明理由

### 5. 校验方案

- [ ] 方案是否解决了核心问题？
- [ ] 是否与现有架构一致？
- [ ] 是否有遗漏的边界情况？
- [ ] 是否可测试？

## 输出格式

```markdown
# [功能名称] 实现方案

## 背景
[问题描述和动机]

## 约束
[技术限制、时间限制、依赖关系]

## 方案对比
| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| A    | ...  | ...  | ✓    |
| B    | ...  | ...  |      |

## 推荐方案：[方案名]
[详细设计，包括文件结构、接口定义、数据流]

## 边界情况
[需要处理的异常和边界]

## 测试策略
[如何验证方案正确性]
```

## Checklist

- [ ] 需求理解无歧义
- [ ] 约束条件已明确
- [ ] 研究了现有实现
- [ ] 查阅了相关文档
- [ ] 提出多个方案并对比
- [ ] 选定方案并详细设计
- [ ] 校验方案可行性
- [ ] 方案文档已保存到 docs/plans/
